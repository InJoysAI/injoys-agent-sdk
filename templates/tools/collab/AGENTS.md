# 协作协议（多 AI 工具 + 用户）

> 所有 `/context-*` 命令开始前先读本文件。目的：让 Codex、Claude Code 等不同工具里的 AI 和用户，知道**谁在说话、谁负责什么、有什么事在等谁**。AI 之间不能实时通信，只通过下面三样东西接力：身份行、花名册、待确认台账。

---

## 1. 身份行

每条命令的**第一行输出**固定为：

```
【<工具> · <角色> · <命令> · <读写属性>】
```

示例：`【codex · 评审 · context-check review assets · 只读（仅可追加台账）】`

- **工具**：自己所在的 AI 工具，用小写 id，如 `claude-code`、`codex`、`cursor`。只写工具，**不写模型名或版本**（AI 对自身版本的认知不可靠）。不确定时写 `未知工具`。
- **角色**：按当前命令确定：

  | 命令 | 角色 |
  |------|------|
  | `context-init`、`context-update`、`context-interview`、`context-collab`、`context-openspec domain/architecture/db/ui/legacy/project/integration` | 生成 |
  | `context-openspec plan/proposal` | 规划 |
  | `context-check` | 评审 |
  | `context-start` | 实现 |

- **读写属性**：`只读` / `可写 .context` / `可写 openspec` / `可写代码`，如实反映本次会修改的范围。
- 花名册里该角色指定的工具与自己不一致时，仍照常执行，并在身份行后加一句 `（花名册指定 <工具>，本次由 <自己> 执行）`，不要拒绝。

## 2. 花名册 `.context/collab/team.md`

每个项目一份，记录**哪个角色默认由哪个工具负责**。格式见 `templates/team.md.template`。

- 推荐用 `.agent/workflows/context-collab.md setup` 交互式配置（见 §7）。所有工具统一从 `.agent/workflows/` 读取命令，不需要为各工具单独安装命令。
- 文件不存在、且当前不是在跑 setup 时，用模板创建（所有角色填 `未指定`），在报告里提示用户运行 `.agent/workflows/context-collab.md setup`；**不要为此中断任务**。
- 只有用户（或用户明确授权）才修改花名册，AI 不自行改派。
- 可取值：`claude-code`、`codex`、`cursor` 等工具 id，`用户`，`未指定`。
- **一个角色可以配多个工具**，用逗号分隔，可在括号里写分工，如 `cursor（前端）, claude-code（后端）`；括号内只是备注，解析时取括号前的工具 id。同一工具也可以兼任多个角色。多工具时的规则见 §8。

| 角色 | 含义 |
|------|------|
| 生成 | 初始化与生成 Context 资产 |
| 规划 | 路线图与提案 |
| 评审 | check，只读核查 |
| 实现 | start，写代码 |
| 工具侧 | 维护 `design/context-dev` 规范本身（不是某个命令） |

## 3. 待确认台账 `.context/history/open-questions.md`

跨会话、跨工具的待确认事项都记在这里。格式见 `templates/open-questions.md.template`；文件不存在时用模板创建。

**每条记录**（标题行 `### Q-<NNN> · <标题>`）包含：

| 字段 | 说明 |
|------|------|
| 发起 | `<工具> (<角色>) · <YYYY-MM-DD HH:mm>`，时间用真实当前时间 |
| 收件 | `@用户` / `@<工具id>` / `@<角色>`（角色按花名册解析为具体工具，可能是多个；解析为 `未指定` 时保持角色名，并在报告里提醒用户指派） |
| 类型 | `问题`（需要回答）/ `裁决`（需要选一个方案）/ `移交`（需要对方接手做某事）/ `认领`（声明自己正在处理某项工作，见 §8） |
| 状态 | `open` → `answered` → `closed` |
| 内容 | 具体要对方确认或做的事；写清选项或期望结果 |
| 证据 | 文件路径 + 章节/行号，对方无需重新检索即可定位 |
| 提案 | 仅 `认领` 类型必填：`- 提案：<提案ID>`，放在「类型」之后，供工具判定同一提案是否已被认领 |
| 答复 | 收件人填写；**必须是记录的最后一个字段**（补充意见追加在其后），便于机器校验“除答复和状态外不得改动” |

**规则**：
- 编号为现有最大编号 + 1，三位数字，不复用。
- 新记录只能**追加**。已有记录只允许两种修改：收件人填写 `答复` 并把状态改为 `answered`；发起人（或用户）确认后把状态改为 `closed`。不得改写他人的内容、证据或删除记录。
- `closed` 的记录保留，作为决策留痕；需要清理由用户决定。
- 台账**不是** Context 输入：不登记到 Manifest `generated_files`，asset-reader 不加载，也不要把里面的结论复制进 README/AGENTS（见 `tools/docs` 的核心文档边界）。已确定的规则应写进 `criterion.md`/ADR，再把台账记录关闭。

## 4. 开工流程（每条命令执行主任务之前）

1. 读取花名册，确认自己的角色（见 §1）；角色配有多个工具时，同时遵守 §8。
2. 读取台账，筛出 `状态: open` 且收件为**自己的工具 id 或自己当前角色**的记录。
3. 若记录与当前任务相关或阻塞当前任务：先处理（回答、或向用户转达），再继续；无关的只在报告里报一个条数。
4. 处理完的记录，按 §3 规则填写答复、改状态。

## 5. 何时写台账，何时直接问用户

- **用户在当前会话里、且问题阻塞当前任务** → 直接问用户。答案若会影响其他工具/后续命令，再补一条台账（状态 `answered`）留痕。
- **需要别的工具/角色决定、核实或接手**，或用户当前不在 → 写台账，不要在会话里丢一句“留待裁决”就结束。
- 评审的 `[AMBIGUOUS]` 必须带收件人：业务取舍 → `@用户`；规范口径 → `@工具侧`；内容层面核实或返工 → 对应角色。同一事项已有 `open`/`answered` 记录时，**不要重复新建**，引用其编号。
- 不要把对话流水、已解决的小问题写进台账。

## 6. 结束报告

命令结束时，报告末尾固定追加：

```
### 待确认
- 发给你的：Q-007 <标题>（open）…（没有则写“无”）
- 发给其他工具的：@codex 1 条（Q-008）；@工具侧 1 条（Q-009）
- 建议下一步：在 <工具> 执行 <命令>，处理 Q-008
```

“建议下一步”只给出有 `open` 记录时的接力建议，不要编造。

## 7. 初始化（`.agent/workflows/context-collab.md setup`）

根据本机实际环境交互式配置花名册。**不要猜测用户装了什么工具，先看证据，再问。**

**Step 1 · 探测（只读）**：命令统一放在 `.agent/workflows/`，**命令目录不能说明用了哪个工具**，不要据此判断。只看各工具自己的入口痕迹，得到**候选工具**（仅是线索，不代表一定在用）：

| 痕迹 | 候选工具 id |
|------|-------------|
| `.claude/`、根目录 `CLAUDE.md` | `claude-code` |
| `~/.codex/` | `codex` |
| `.cursor/` | `cursor` |
| `.devin/`、`.qoder/`、`.grok/` | `devin` / `qoder` / `grok` |

同时读取现有 `.context/collab/team.md`（若有）和台账中 `open` 的条数。当前自己所在的工具（身份行里的工具）一定是候选。

**Step 2 · 询问用户**（有 AskUserQuestion 工具就用它，否则用编号列表在对话中问，一次只问一件事）：
1. **你实际在用哪些 AI 工具？** 列出候选并允许补充（用户可能还在用没有痕迹的工具）。
2. **各角色由谁负责？** 对 `生成` / `规划` / `评审` / `实现` / `工具侧` 逐一选择工具；**可多选**（如实现有两个工具），也可为多选工具写分工备注；同一工具可兼任多个角色。给出建议：若有两个及以上工具，`评审` 与 `实现` 尽量不是同一个（独立核查）；只有一个工具时全部填它。
3. 评审有多个工具时，问清评审方式：**串行**（一个评审完、你检查后再交给下一位）还是**并行**（同时独立评审），写入花名册的“评审方式”行。
3. 工具侧不需要 AI 常驻时，可填 `用户`。

**Step 3 · 写入**：
- 以 `templates/team.md.template` 为底，把答案填入“负责工具”列；工具 id 只用小写 id（`claude-code`、`codex`、`cursor`、`antigravity`、`devin`、`qoder`、`grok`、`用户`）。
- 已有花名册时，先展示变更对比并得到用户确认再覆盖。
- 确保 `.context/history/open-questions.md` 存在（缺失则用模板创建）。
- **只写这两个文件**，不改其他任何文件。

**Step 4 · 报告**：
- 输出最终花名册表。
- 提示各工具启动时都从 `.agent/workflows/` 读取命令；若某工具读不到该目录，由用户自行决定如何接入，本流程不负责安装。
- 提醒：花名册只由用户修改，之后想改派可再次运行 `setup`。

## 8. 一个角色有多个工具（评审、实现等）

花名册允许同一角色配多个工具。为避免重复劳动和互相覆盖：

- **发给角色的记录（`@评审` 等）**：角色里**任何一个**工具都可以处理。先处理的工具在 `答复` 里署上自己的工具 id 并改状态；其他工具看到状态不再是 `open` 就不要重复处理，需要补充意见时在 `答复` 后追加一行带工具 id 的补充，不改他人已写的内容。
- **多个评审：串行、并行都支持，由花名册的「评审方式」决定**（默认串行）。在花名册表格下方用一行 `评审方式：串行` 或 `评审方式：并行` 指定；用户也可以在某次命令里临时说明（如“本次 codex 和 cursor 并行”或“这次按顺序”），临时说明优先于花名册。
  - **串行**：花名册里「评审」的**书写顺序就是评审顺序**。一个评审完成后，用户检查，没有问题再交给下一位，AI 之间不自动接力。
    - 开工时，找出自己的前一位评审，读取台账中前一位发起的记录：仍是 `open` / `answered` 的（用户还没确认关闭）→ 先报告给用户并停下，等用户明确说继续；都已 `closed` 或没有 → 正常开工。
    - 前一位已 `closed` 的事项**不要重复报告**，只引用其编号；只评审前一位没覆盖的、或修复后需要复核的部分。自己是第一位时没有前置条件。
    - 结束报告的「建议下一步」写“交给 <下一位评审工具>”；自己是最后一位则写“评审链已走完”。
  - **并行**：评审之间互不等待、互不依赖，目的就是独立交叉核查。
    - 开工时**不要先读其他评审的结论**来影响自己的判断（可以读台账里发给自己的记录）；评审结束后再读台账，把同一事项合并引用。
    - 所有产出都带自己的工具 id：台账记录的 `发起` 字段本来就有；若本次评审要写文件（如提案评审结果），文件名加 `-<工具id>` 后缀，避免多个评审写同一路径互相覆盖。
    - 同一事项台账已有 `open`/`answered` 记录时，只引用其编号并补一行署名意见，不新建。
    - 结束报告的「建议下一步」写“等其他评审完成后，由你汇总”，不要代为汇总其他评审的结论。
  - **两种方式共同的**：意见不一致时各自署名写明，由 `@用户` 裁决；汇总、取舍、关闭记录由用户决定。
- **多个实现并行**：同一个提案（`context-start <提案ID>`）同一时间只能有一个工具在做。开工前先查台账：已有他人的 `认领` 记录且状态为 `open` → 停止并报告给用户；没有 → 追加一条 `认领`（`提案：<提案ID>`，内容写自己负责的范围），归档完成或放弃时改为 `closed`。不同提案可以由不同工具并行。判定“同一提案”只看 `认领` 记录的 `提案：<提案ID>` 字段，不解析自由文本。
- **分工备注**（如 `cursor（前端）`）只是提示，不构成权限限制；超出备注范围的工作先问用户。

## 9. 协议版本与机器校验

- 花名册和台账的头部各有一行 `协议版本：1`。字段名、状态机或格式发生不兼容变化时版本号递增；自动化工具（如 DSH 适配层）应在版本不识别时**报错停止**，不要猜测解析。缺失该行视为旧文件，按版本 1 处理并给出警告。
- 校验脚本：`node design/context-dev/scripts/check-collab-ledger.mjs [项目根]`
  - 检查花名册（角色齐全、评审多工具时必须有评审方式）和台账（标题、字段、编号递增、类型/状态取值、`认领` 必须有 `提案`、`answered` 必须有答复、收件项是否在花名册中）。
  - 与旧版比较：`--base-ref <git-ref>`（或 `--base-file <文件>`）检查“只追加、不删除、除答复和状态外不得改动、状态只能前进、新记录编号 = 最大编号 + 1”。
  - 加 `--actor <工具id|用户>` 检查授权：只有收件人能答复，只有发起人或用户能关闭。
  - 退出码 0 通过（可有警告）、1 有错误。无人值守的写入方（适配层、CI）应在写入前后各校验一次。
