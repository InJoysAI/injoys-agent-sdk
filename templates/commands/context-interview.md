# Context Interview

通过深入、探究式的访谈，将草稿规格说明转化为完整的技术文档，或从零开始探索需求。

## 使用模式

### 模式1: 完善现有文档
基于现有文档进行深度访谈并更新该文档。

```
.agents/workflows/context-interview.md
目标文档: @openspec/proposal-roadmap.md
```

### 模式2: 需求探索（更新 .context）
从对话开始探索需求或技术细节，根据主题更新对应的 `.context/` 文件。

```
.agents/workflows/context-interview.md
主题: 用户认证的业务规则
```

**主题映射到 .context 目录：**
| 主题类型 | 目标文件 |
|---------|---------|
| 业务规则、用户故事 | `.context/domain/business_rules.md` |
| 用户旅程、交互流程 | `.context/domain/user_journeys.md` |
| 系统设计、组件架构 | `.context/architecture/system_design.md` |
| 技术栈、依赖 | `.context/architecture/tech_stack.md` |
| API 策略、接口设计 | `.context/architecture/api_strategy.md` |
| 安全策略、权限 | `.context/architecture/security_policy.md` |
| UI/UX 设计 | `.context/ui/` 相关文件 |
| 项目准则 | `.context/criterion.md` |

## 触发条件

- 存在 `proposal-roadmap.md` 或用户指定文档需要通过系统性提问来完善需求
- 触发词："帮我完善这个 plan"、"问我关于项目的问题"、"讨论一下需求"
- 草稿规格需要全面细化时
- 需要从零开始探索某个领域的需求或技术决策

## 访谈原则

1. **先查后问**：能从 `.context/`、目标文档、`openspec/`、代码库读到答案的，直接读，不要拿来问用户；只问需要用户做决定或只有用户知道的事。
2. **决策树，分轮推进**：把待决策点画成依赖树。每一轮只问“前置决策都已确定”的那一批（frontier）；依赖未定答案的问题放到下一轮，避免基于猜测提问。
3. **每题带推荐答案**：每个问题给出你的推荐选项和一句理由，措辞让用户回答“同意/是”即表示采纳推荐。用户只需否决或修正。
4. **每轮 2–5 题，编号**，格式固定，便于逐条回答：

   ```
   ❓ Q1 登录失败锁定策略
   连续失败几次后锁定？锁定多久？
   ➡️ 推荐：5 次失败锁定 30 分钟（与现有 criterion 的安全基线一致）
   ```
5. **追问到可落地**：回答含糊（“看情况”“一般”）时继续追问到可写成规则、数值或验收条件。
6. **边问边记**：每轮结束后在内部维护“已决策 / 待确认 / 被否决方案”清单，最终写入文档，不依赖记忆。

## 执行流程

1. **确定访谈模式**
   - 用户指定了文档 → 模式1（完善文档）
   - 用户指定了主题 → 模式2（需求探索）
   - 都未指定 → 询问用户

2. **读取相关上下文**
   - 模式1: 读取目标文档
   - 模式2: 读取 `.context/` 下对应领域的现有内容
   - 必要时读取相关 `source/` 与代码，先排除“已有答案”的问题

3. **建立决策树并列出覆盖清单**
   - 识别需要完善的领域：技术实现、UI/UX、边缘情况、风险、权衡取舍、架构决策（见下“覆盖维度”）
   - 找出文档里的矛盾、空白、`TODO`/`待定`/`[AMBIGUOUS]` 项，作为首批问题

4. **分轮访谈**
   - 按“访谈原则”提问；可使用宿主工具提供的交互式提问能力（如有），否则直接用对话提问
   - 每轮收到回答后，更新决策树，再问下一批；用户说“按推荐”则整批采纳

5. **覆盖维度（按需）**
   - **技术实现**: 技术栈、性能要求、扩展性
   - **UI/UX**: 用户流程、交互模式、无障碍
   - **边缘情况**: 异常处理、并发、数据边界、空状态、失败重试
   - **风险考量**: 安全、依赖、技术债务、合规
   - **权衡取舍**: 方案对比、优缺点
   - **架构决策**: 组件划分、接口设计、数据流
   - **范围与验收**: 不做什么、上线标准、如何验证
   - **迁移与兼容**: 现有数据、旧接口、回滚

6. **收尾确认（必须执行，不得省略）**

   > 访谈中途觉得“问完了”不算结束。往往遗漏的恰恰是没人想到要问的事。

   a. **自查遗漏**：对照“覆盖维度”逐项核对，列出本次**没有讨论过**的维度，以及文档里仍存在的矛盾、`待定`、未回答的问题。
   b. **向用户展示决策摘要**：已确定的决策、仍待确认的事项、被否决的方案，让用户能快速核对。
   c. **主动询问**（单独一问，不与其他问题合并）：

      ```
      ❓ 收尾确认
      以上是目前确定的决策。以下维度我们还没聊到：[遗漏维度清单]
      你是否还有其他疑问、担心或想补充的内容？（例如：没想清楚的地方、外部约束、与其他团队/系统的依赖）
      ➡️ 若没有，回复“没有”即可开始写入文档。
      ```
   d. 用户补充了内容 → 回到第 4 步针对新内容访谈，**完成后再次收尾确认**；直到用户明确回复“没有”。
   e. 用户没有回应或回复含糊时，不视为“没有”，再确认一次；仍无答复则把相关点作为“待确认”写入文档，不得擅自当作已决策。

7. **更新目标文件**（收尾确认通过之后）
   - 模式1: 更新用户指定的文档
   - 模式2: 更新 `.context/` 下对应的文件
   - 只写已决策的内容；未决事项标记为“待确认”并注明负责人或前置条件
   - 保留被否决方案及理由（简短），避免后续重复讨论

8. **结束访谈**
   - 输出访谈总结：主要决策点、更新的文件、仍待确认的事项
   - 建议下一步：改动了 `.context/` 时运行 `.agents/workflows/context-check.md` 校验一致性
